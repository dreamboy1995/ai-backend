
## Sprint 9 —— 自修复循环与端到端验证
这是 P3（Agent 化）阶段的最后一个 Sprint，也是让 Agent 从“能干活”进化到“能干好活”的关键。上一个 Sprint 结束后，Agent 已经能“写代码、跑命令”，但它的工作流是线性的——写完就结束，代码能不能跑通它不管。

S9 要赋予 Agent “试错与迭代” 的能力：它会主动运行代码/测试，捕获报错信息，分析原因，自动修改代码，然后重新运行，直到成功或达到重试上限。这是 Agent 走向“独立开发者”的临门一脚。


### #### 核心目标（S9）
自修复闭环与测试沙箱：实现 “执行 → 报错捕获 → 错误定位 → 自动修复 → 重跑验证” 的完整自愈循环；集成常用测试框架（pytest、jest）作为验证沙箱；插件端完整展示每次“修复尝试”的 Diff 变化和错误栈，让用户全程可监督。


### 👥 人员分工（S9 后端算法与前端体验并重）
- 后端/算法（1-2人）：错误解析器（堆栈追踪 → 精准定位）、自修复 Prompt 工程、重试状态机、测试框架集成适配器。

- 插件开发（1人）：Builder 面板中的“修复尝试”时间线 UI、错误高亮与跳转、重试计数组件。


### 📅 每日拆解任务（第 81-90 个工作日）

### 🔧 S9 关键技术预研与风险预警（研发必读）
|风险点	|应对方案|
|---|---|
|无限修复循环（最危险）	|模型可能把一个错误修好，却引入了另一个新错误，导致重试永无止境。强制约束：① 最大重试次数 3 次。② 每次重试必须产生 不同的 Diff（若与上一次 Diff 相同，立即终止）。③ 连续 2 次新错误类型不同，立即终止（说明模型在“拆东墙补西墙”）。|
|后台进程残留	|Agent 可能通过 run_command 启动了长期运行的 Web 服务（如 python app.py）。如果不加管控，会遗留大量僵尸进程。解决方案：Agent 在启动服务时，必须使用 nohup 或 pm2，并在任务结束时（或用户关闭 Builder）主动发送 SIGTERM 杀掉所有子进程。更好的是，在 Sandbox（Docker）中运行，任务结束直接销毁容器。|
|测试套件依赖复杂	|有些项目需要先 npm install 才能跑 npm test。Agent 如果直接跑测试，会报依赖缺失。在 run_tests 工具中，需要先检测 node_modules 或 venv 是否存在，不存在则自动先执行依赖安装（npm install / pip install -r requirements.txt）。|
|大模型“幻觉修复”	|模型可能把错误的代码改成“看起来对但实际不对”的样子（比如把 x 改成 y，但 y 依然没定义）。这种情况下，测试用例是唯一可靠的验证手段。所以 测试沙箱是自修复循环不可或缺的终点裁判，必须强制 Agent 在有测试的项目里跑通测试才算成功。|
