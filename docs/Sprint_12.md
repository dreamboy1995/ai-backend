
## Sprint 12（第23-24周）——原生 IDE 调研与 P4 收官。

如果说前 11 个 Sprint 是在“造车”，那 S12 就是为“造飞机”做技术预研。我们不一定要真的去 Fork VS Code（那是巨大的工程投入），但必须在这个节点完成 可行性调研和技术储备，为后续的战略决策提供依据。

同时，S12 也是整个 6 个月开发计划的 收官总结——回顾成果、规划长期演进路线，为产品从“MVP”走向“商业化”铺平道路。


### Sprint 12 核心目标（S12）
战略展望与技术储备：完成对 VS Code 源码 Fork 改造的技术调研，输出可行性报告；实现“长上下文”优化（支持 200K Token 输入的 Monorepo 场景）；基于 S10-S11 的数据积累，为后续 Cue 模型训练做好数据准备；完成 P4 阶段成果总结与未来 6 个月路线图规划。

#### 第 113-114 天（长上下文优化 — 让 Agent 能“读”大型 Monorepo）
Builder 模式在处理大型 Monorepo（如 10000+ 文件的微服务项目）时，上下文窗口容易爆炸。S12 要解决这个问题。

| 角色       | 具体任务（核心算法）	                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |验收标准|
|------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|---|
| 算法工程师 | 1. 实现 “渐进式上下文加载” 策略：<br>&nbsp;- 当 Builder 启动时，不 索引全仓库（耗时太长），而是 按需加载：<br>&nbsp;&nbsp;a. 第一层：当前光标所在文件 + 其直接 import 的文件（深度 1）。<br>&nbsp;&nbsp;b. 第二层：如果 Agent 在执行步骤时发现缺少依赖，触发 grep_search 动态补充上下文。<br>&nbsp;&nbsp;c. 第三层：用户通过 #文件夹 手动引用的范围。<br>2. 上下文摘要（Summarization）：<br>&nbsp;- 对于超过 1000 行的文件，调用大模型生成 “文档字符串级摘要”（文件概览 + 主要导出函数列表），将 1000 行压缩为 200 个 Token 的摘要。<br>&nbsp;- 将摘要存入 Redis 缓存（TTL=1 天），避免反复生成。<br>3. 测试验证：在一个包含 500 个文件的真实 React 项目上运行 Builder，观察 Token 消耗。	 |在相同任务下，优化前的 Token 消耗为 15000，优化后降至 6000（节省 60%）。Agent 完成任务的步骤数未明显增加（摘要没有丢失关键信息）。|
| 后端       | 1. 将“摘要生成”封装为独立微服务，当大模型 API 空闲时在后台批量生成未缓存文件的摘要。	                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       |-|

⚠️ 摘要的“精度与丢失”平衡：摘要不能太简略（丢失关键 API 信息），也不能太详细（压缩效果差）。提示词模板："请用 3-5 句话概括这个文件的主要功能，并列出所有导出的函数/类名及其简短描述"。经测试，这种格式的摘要对 Builder 任务的完成率影响 < 5%，但 Token 节省显著。


#### 第 115-116 天（Cue 预测模型的数据准备 — 从规则到学习）
S6 的 Cue 是基于规则的（启发式），准确率约 60%。为了在 P4 阶段将其提升到 80%+，我们需要准备训练一个 “专用 Cue 预测模型” 的数据。

|角色	|具体任务（数据工程）	|验收标准|
|---|---|---|
|算法工程师	|1. 从 S10 的埋点数据库中，提取 Cue 相关的正负样本：<br>&nbsp;- 正样本：用户点击了 Cue 箭头，且跳转后 30 秒内做了修改（说明预测准确）。<br>&nbsp;- 负样本：Cue 箭头出现但用户从未点击（说明预测不准，用户无视了）。<br>2. 特征工程：为每个 Cue 预测构建特征向量：<br>&nbsp;- 用户当前编辑的文件路径、最近修改的行号。<br>&nbsp;- 被预测文件的路径、符号名、与当前文件的依赖关系（来自 S4 的 Call Graph）。<br>&nbsp;- 用户的历史行为特征（如“该用户经常先改 A 再改 B”的序列模式）。<br>3. 将正负样本按 8:2 切分为训练集和测试集，保存为 ./data/cue_dataset_v1.parquet。	|数据集包含至少 5000 个样本（正负各半），特征维度约 20 列。使用简单模型（如 XGBoost）做快速验证，AUC > 0.75（说明特征有效）。|
|技术架构师	|1. 设计 “Cue 模型服务化”架构：后续 S13（计划外）可将该模型部署为独立微服务，实时接收用户编辑上下文，返回预测位置。	|架构设计文档完成，包含 API 设计、模型更新策略、AB 测试方案。|

💡 为什么 S12 只准备数据，而不实际训练 Cue 模型？ Cue 模型的训练需要一个独立 Sprint（约 2 周），包括模型选型（推荐 LightGBM 或小型 Transformer）、超参数调优和在线部署。S12 的时间窗口不足以完成，因此将其规划为 S13（未来 2 个月内的追加 Sprint），本次只完成数据准备和架构设计。

### 🔧 S12 关键技术预研与风险预警（研发必读）
|风险点	|应对方案|
|---|---|
|VS Code Fork 维护成本高	|初期建议走“插件路线”，仅当用户规模、商业收入足够支撑 5-10 人的专职维护团队时，再启动 Fork 项目。S12 的调研报告应明确给出“触发 Fork 的量化条件”（如：付费用户 > 1000 人，年收入 > 500 万）。|
|长上下文摘要的质量不稳定	|摘要生成依赖大模型，模型偶尔会“幻觉”出不存在的函数名。解决方案：在摘要中加入 “置信度” 字段，若置信度 < 0.8，则该文件不走摘要策略，直接加载原文（保证准确性优先）。|
|Cue 数据集正负样本不平衡	|如果负样本远多于正样本（用户大多不点 Cue），训练时会偏向“预测无位置”。解决策略：欠采样（随机丢弃部分负样本）或过采样（对正样本做 SMOTE 增强），使正负比接近 1:1。|
|团队动力与 burnout	|6 个月的密集开发后，团队可能进入疲劳期。S12 应安排 “轻松周”（减少任务量，侧重调研和文档），并组织团建活动，为下一阶段蓄力。|
