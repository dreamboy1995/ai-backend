
## Sprint 11 —— FIM 补全模型训练与推理优化
这是整个项目技术含量最高的 Sprint 之一，也是从“调用别人 API”走向“拥有自主模型能力”的关键转折。S11 的目标不是训练一个全能大模型，而是训练一个 “小而专”的 FIM（Fill-in-the-Middle）补全模型。

这个模型只做一件事——行级/块级代码补全，不需要懂对话、不需要解 LeetCode、不需要写 Builder 计划。因为任务单一，所以可以把参数量压到 1.3B~6.7B，实现 <300ms 的本地/云端推理延迟，大幅降低 API 调用成本，同时提升补全的流畅度。


### 核心目标（S11）
训练并部署专用的 FIM 代码补全模型：基于开源基座模型（DeepSeek-Coder / StarCoder）进行 FIM 格式的微调（LoRA 或全量）；将训练好的模型量化（GPTQ/AWQ）并封装为独立推理服务；在主网关中实现“智能路由”——行内补全走小模型（快+便宜），复杂推理走大模型（慢+强）。


### 👥 人员分工（S11 需算法/MLOps 深度参与）
- 算法工程师（1-2人）：FIM 数据构建、模型微调（LoRA/全量）、超参数调优、量化与推理优化。

- 后端/MLOps 工程师（1人）：推理服务封装（TensorRT-LLM / vLLM / llama.cpp）、Docker 镜像构建、GPU 资源调度、路由策略实现。

- 插件开发（1人）：接入新的补全接口，实现“打字时自动触发补全”的交互（类似 Cursor 的灰色幽灵文字）。


### 📅 每日拆解任务（第 101-110 个工作日）
#### 第 101-102 天（FIM 训练数据构建 — 从“普通代码”到“完形填空”）
FIM（Fill-in-the-Middle）是代码补全模型的专用训练范式。它不是让模型读完整代码，而是故意“挖空”中间部分，让模型学习根据上下文（前文 + 后文）补全中间内容。这恰好就是“代码补全”的真实场景。

|------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|---|
| 算法       | 1. 从三个来源收集训练语料（总计目标：50 亿 Token）：<br>&nbsp;- 公开数据：The Stack（GitHub 公开代码）、StarCoder Data，优先选 Python / JavaScript / TypeScript / Java / Go。<br>&nbsp;- 内部数据：S10 收集的用户代码（经脱敏处理）。<br>&nbsp;- 高质量合成数据：从 S10 的 SFT 数据中反向生成 FIM 样本（将正确代码的中间某段挖空，让模型填空）。<br>2. 编写 fim_data_builder.py，实现 FIM 分割策略（参考 CodeLlama 论文）：<br>&nbsp;- 按 文件级 随机选择三种模式之一（概率各 1/3）：<br>&nbsp;&nbsp;a. PSM（Prefix-Suffix-Middle）：<fim_prefix> 前半段 <fim_suffix> 后半段 <fim_middle> 中间（需预测）。<br>&nbsp;&nbsp;b. SPM（Suffix-Prefix-Middle）：<fim_suffix> 后半段 <fim_prefix> 前半段 <fim_middle> 中间。<br>&nbsp;&nbsp;c. PMS（Prefix-Middle-Suffix）：<fim_prefix> 前半段 <fim_middle> 中间 <fim_suffix> 后半段。<br>&nbsp;- 严格控制“挖空”比例：被挖空的中间部分长度占总代码长度的 20%~50%（太短无意义，太长难度过高）。<br>3. 将处理好的数据打包为 内存映射格式（如 Arrow 或 MMap），方便训练时高速读取。	运行脚本处理 10000 个代码文件，产出 50000 个 FIM 训练样本，每个样本包含 input_ids 和 labels（被挖空的中间部分为 label）。 |样本 Token 总量约 2 亿。|

|------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|---|
| 算法       | 1. 基座模型选型（基于参数量、推理速度、代码能力权衡）：<br>&nbsp;- Option A（轻量级，首选）：deepseek-coder-1.3b-base（参数量 1.3B，CPU 可跑，INT8 量化后仅 1.2GB）。<br>&nbsp;- Option B（平衡）：deepseek-coder-6.7b-base（参数量 6.7B，需 GPU，但补全质量更高）。<br>&nbsp;- 决策建议：先训练 1.3B 版本（迭代快，适合验证流程），S12 再升级 6.7B。<br>2. 编写 fim_trainer.py，采用 LoRA（低秩适配） 微调（而非全量微调），原因：<br>&nbsp;- 训练速度快（只更新 0.5%~2% 的参数）。<br>&nbsp;- 可插拔：保留基座模型不变，只替换 LoRA Adapter。<br>&nbsp;- 显存要求低（1.3B + LoRA 只需 ~20GB 显存）。<br>3. 设置超参数：<br>&nbsp;- learning_rate=2e-4，batch_size=16（梯度累积 4 步），epochs=2。<br>&nbsp;- 使用 packing=True 将短样本拼接，提高训练效率。	 |启动一次 1000 步的快速试跑（Dry Run），Loss 从 ~4.5 开始下降，确认训练脚本无报错。|

💡 为什么选 LoRA 而非全量微调？ 全量微调需要更新全部参数，容易造成“灾难性遗忘”（模型忘了原始能力）。LoRA 只改变少量参数，能更好地保留基座模型原有的代码理解能力，同时专项提升 FIM 补全能力。推理时，我们可以把 LoRA 权重合并进基座模型，不增加额外推理开销。

### 📂 关键接口/数据结构变更（S11 新增）
1. FIM 补全接口（推理服务）
```typescript
POST /v1/completions/fim
Request: {
  prefix: string;    // 光标前文（如 "def add(a, b):\n    "）
  suffix: string;    // 光标后文（如 "\n    return result"）
  max_tokens: number; // 最大生成长度，默认 64（行级补全够用）
  temperature: number; // 默认 0（确定性输出，补全要稳定）
}
Response: {
  completion: string; // 补全内容（如 "result = a + b\n"）
  finish_reason: 'stop' | 'length';
  usage: { total_tokens: number };
}
```

2. 插件端新增设置项
```typescript
interface GlobalState {
  // ... 原有字段
  enable_auto_completion: boolean;        // 默认 true
  completion_trigger_delay: number;       // 防抖延迟（ms），默认 500
  completion_model_source: 'local' | 'cloud'; // 本地模型 or 云端小模型实例
  fim_model_downloaded: boolean;          // 是否已下载量化模型文件
}
```

3. 路由决策逻辑（伪代码）

```python
def route_request(request):
    if request.mode == 'completion':
        if local_fim_model_available and not overloaded:
            return call_local_fim_model(request)
        else:
            return call_cloud_fim_fallback(request)  # 也可调用云端大模型，但限定 max_tokens=64，降低延迟
    else:
        return call_cloud_large_model(request)  # Chat / Builder
```


### 🔧 S11 关键技术预研与风险预警（研发必读）
| 风险点                 | 应对方案                                                                                                                                                                                                                                 |
|------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| 训练数据过拟合         | FIM 模型如果只在特定库（如 PyTorch）的代码上训练，在其他库（如 Django）上表现会差。务必保证训练语料的 语言分布均衡：Python 30%、JavaScript 25%、TypeScript 15%、Java 15%、Go 10%、其他 5%。训练时使用 --dataset_mixture 参数按比例采样。
| 显存不足（OOM）        | 1.3B 模型 + LoRA 在 FP16 下约需 12GB 显存。如果只有 8GB 显卡，改用 QLoRA（4-bit 量化微调），显存需求降至 6GB。我们提供的 Docker 镜像默认启用 QLoRA。
| 本地模型下载分发       | 量化后的模型文件约 1GB，如何让用户快速下载？方案：① 在插件首次启动时，使用 vscode.window.withProgress 显示下载进度条，从 CDN（OSS/CloudFront）下载。② 支持离线安装包（用户手动下载 .bin 放到指定目录）。
| 幽灵文字闪烁/卡顿      | VS Code 的 Decoration 如果频繁刷新，会导致编辑器卡顿。必须严格执行“500ms 防抖”，并在用户输入时立即清除当前 Decoration（保证不残留旧补全）。
| 补全质量不如云端大模型 | 这是意料之中的。但我们的策略是 速度换质量：行内补全只需要 80% 的准确率就足够辅助开发，用户按 Tab 或继续打字只需要 300ms 响应。如果用户想要“整函数生成”，他们依然可以用 Ctrl+K Inline Chat 调用大模型。两者形成互补。
