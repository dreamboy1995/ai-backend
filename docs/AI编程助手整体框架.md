# 类 Trae 的 AI 编程助手整体框架

结合 Trae 等主流产品的核心能力（Builder 模式、智能对话、上下文理解、工具调用、多模型支持），建议采用以下分层架构：

## 一、总体架构
| 层次       | 内容                                              |
|------------|---------------------------------------------------|
| 交互层     | IDE 编辑器 / 侧边Chat / 内嵌Chat / Builder面板    |
| 智能体层   | 任务规划 → 代码生成 → 工具调用 → 自检验修复       |
| 上下文引擎 | 代码库索引 / 混合检索 / 上下文组装 / 位置预测     |
| 模型层     | 多模型接入 / 路由切换 / 补全专用小模型 / 流式输出 |
| 工具执行层 | 文件读写 / 终端命令 / Git / 测试沙箱 / 预览       |
| 后端服务   | API网关 / 会话管理 / RAG服务 / 评测与数据回流     |

## 二、各层核心设计

### 1.交互层（产品形态）
载体选择：初期做 VS Code / JetBrains 插件（成本低、分发快），后期可 fork VS Code 做原生 IDE（类 Cursor/Trae 路线）
三种核心交互：
侧边 Chat：讲解代码、答疑、生成片段
内嵌对话（Inline Chat / Ctrl+K）：选中代码就地修改
Builder 模式：输入需求，从 0 到 1 生成完整项目（数据库设计 + API + 前端页面），这是类 Trae 的差异化重点
支持 @文件、@代码块、@文件夹 引用与截图输入

### 2. 智能体层
Planner：将自然语言需求拆解为任务步骤（分析需求 → 设计方案 → 生成代码 → 运行验证）
Tool Use 系统：让模型能调用文件读写、终端命令执行、代码搜索、运行测试等工具（建议基于 MCP 协议，生态兼容性好）
自修复循环：执行报错 → 读取报错信息 → 自动修复 → 重跑验证

### 3.上下文引擎（决定产品上限的关键）
代码索引：tree-sitter 做 AST 解析 + 代码切片 + Embedding 向量化（符号表 + 依赖关系图）
混合检索：向量检索 + 关键词/符号检索 + 重排序
上下文组装：当前文件、光标位置、打开的 Tab、Git diff、对话历史动态拼装，控制 token 预算
编辑位置预测：类 Trae 的 Cue 能力，预测用户下一步修改位置

### 4.模型层
多模型路由：对话/推理用大模型（DeepSeek-R1/V3、GPT-4o、Claude 系列、Doubao），支持用户切换
补全专用模型：小参数量 FIM（Fill-in-the-Middle）模型做行级/块级补全，保证低延迟（<300ms）
统一 LLM 网关，屏蔽不同模型 API 差异，支持流式输出

### 5.后端与安全
网关：鉴权、限流、计费、审计
向量数据库：pgvector / Milvus
安全合规：代码隐私（索引可本地化）、工具调用白名单、危险命令需用户确认、生成代码的许可证检测

## 三、总体排期概览（Sprint 1-12）
| 阶段	         | Sprint 周期	    | 核心主题     | 并行流（前端/插件端）             | 并行流（后端/算法端）                |
|--------------|----------------|--------------|-----------------------------------|--------------------------------------|
| P1（MVP）    | S1-S3（6周）   | 	地基与对话   | 	插件骨架、Webview UI、鉴权        | 统一网关、会话管理、基础RAG          |
| P2（上下文） | S4-S6（6周）   | 	理解与编辑   | Inline Chat、Diff预览、多Tab管理  | AST索引、混合检索、上下文组装        |
| P3（Agent）  | S7-S9（6周）   | 	自动化与执行 | Builder面板、终端集成、Diff确认流 | Planner拆解、MCP工具调用、自修复循环 |
| P4（长期）   | S10-S12（6周） | 打磨与专有化 | 用户体验打磨、遥测埋点            | FIM小模型训练、评测集构建、数据飞轮  |

## 详细细化拆解（WBS 颗粒度）
### 🔹 第一阶段 P1：MVP 核心链路（S1-S3）
目标：跑通“登录 -> 侧边栏问答 -> 单文件 Apply”闭环。

- S1（第1-2周）：工程基建 & 插件壳子

  - 插件端：搭建 VS Code 插件脚手架（yo code），配置 Webview 面板（React/Vue），实现侧边栏 Chat UI 静态布局（消息气泡、Markdown渲染、代码高亮）。

  - 后端：搭建 API 网关（鉴权 JWT），对接第三方模型（如 DeepSeek-V3）的基础 Completions API，实现流式 SSE 透传。

  - 交付物：插件可成功安装，能发消息并看到流式返回的“Hello World”文本。

- S2（第3-4周）：对话上下文基础 & 文件操作

  - 插件端：实现 @文件 提及功能（读取当前编辑器选中文本/整个文件内容，拼入 User Prompt）。增加“Apply”按钮（将模型返回的代码块插入当前光标位置）。

  - 后端：实现会话管理（Session ID），支持多轮对话历史裁剪（基础滑动窗口）。

  - 难点攻克：解决 VS Code 文本编辑器的 EditBuilder 并发冲突问题。

- S3（第5-6周）：单文件生成 & 上线验证

  - 插件端：增加 /new 指令（输入需求，生成单个 .py/.js 文件并自动保存）。增加用户设置项（API Key/模型切换下拉框）。

  - 后端：增加 Token 计费统计和限频策略（防滥用）。

  - 验收：用户无需离开 IDE，即可通过对话生成一个可运行的 Python 脚本并保存。

### 🔹 第二阶段 P2：上下文理解与编辑增强（S4-S6）
目标：AI 能“懂”整个仓库，支持选中文档局部修改。

- S4（第7-8周）：本地索引基建（AST + 向量化）

  - 后端/本地服务：集成 tree-sitter 解析多语言（Python/JS/Java/Go），提取符号表（函数/类/变量）。搭建轻量级向量数据库（推荐 pgvector 或 milvus-lite）。

  - 插件端：增加 .gitignore 监听，文件变动时触发增量索引更新（避免 CPU 飙高）。

  - 交付物：插件后台静默完成代码库的首次向量化。

- S5（第9-10周）：混合检索与上下文组装（RAG）

  - 算法端：实现“关键词（BM25）+ 向量（Embedding）”混合检索，引入 Rerank（重排序）模型优化前三名命中率。

  - 上下文工程：实现动态上下文组装策略——按优先级排序（光标附近 > 当前打开Tab > Git Diff > 全局检索结果），并计算 Token 预算（预留 20% buffer 给模型输出）。

  - 插件端：在 Chat 输入框支持 #代码块 引用（用户选中代码片段手动喂给 RAG）。

- S6（第11-12周）：Inline Chat 与 Diff 预览

  - 插件端核心：实现 Ctrl+K 内嵌对话（在编辑器选中区域弹出悬浮输入框），修改代码后以 Diff 视图（绿色新增/红色删除） 呈现变更，用户点击“接受”才写入文件。

  - 后端：提供多文件编辑的 Structured Output（强制模型输出 JSON 格式：{"file_path": "a.py", "new_content": "..."}）。

  - 验收：针对现有代码选中函数，输入“优化性能”，能生成 Diff 并手动确认应用。

### 🔹 第三阶段 P3：Agent 化与 Builder 模式（S7-S9）
目标：从“回答问题”进化为“自主完成任务”，这是类 Trae 的差异化核心。

- S7（第13-14周）：Planner（任务规划器）与 ReAct 框架

  - 后端：设计 Agent 核心循环（ReAct：思考 -> 行动 -> 观察）。实现 Planner 模块，将模糊需求（如“做一个 Todo 全栈应用”）拆解为 DAG 任务图（任务 A: 设计数据库表 -> B: 编写 CRUD API -> C: 构建前端页面）。

  - 插件端：新增 Builder 面板（独立于 Chat 的宽屏视图），展示任务规划进度的“思维链”（类似 Trae 的步骤列表勾选）。

- S8（第15-16周）：工具调用（MCP 协议落地）

  - 后端：落地 MCP（模型上下文协议），封装标准工具集：

    - read_file / write_file（带行号定位）

    - run_terminal（执行 npm/pip 命令，需用户点击确认执行）

    - grep_search（代码内搜索）

    - git_commit（自动生成 commit message）。

  - 安全机制：实现工具调用“白名单”和敏感命令（如 rm -rf）的强拦截弹窗。

- S9（第17-18周）：自修复循环与沙箱执行

  - 算法端：实现 自修复（Self-Correction） 闭环：Agent 执行终端命令 -> 捕获 stdout/stderr -> 报错信息喂回大模型 -> 模型重新生成修正后的命令/代码 -> 重跑验证（循环上限设为 3 次）。

  - 后端：集成轻量级沙箱（如 Docker 或 run_code 隔离环境），防止 AI 生成的恶意代码破坏宿主机环境。

  - 交付物：输入“创建一个 Flask 项目并运行 Hello World”，Agent 能一步步创建文件、安装依赖、启动服务，并在报错端口被占用时自动换端口重试。

### 🔹 第四阶段 P4：差异化壁垒与专有模型（S10-S12+）
目标：摆脱纯 API 调用，建立低成本、高体验的护城河。

- S10（第19-20周）：数据飞轮与评测体系

  - 数据基建：全链路埋点（用户采纳率、手动修改率、Backspace 撤销率）。搭建标注后台，人工标注 Bad Case。

  - 评测体系：建立自动化评测流水线，跑通 HumanEval / MBPP 基准测试，并建立内部的“场景化评测集”（如 React 组件生成、SQL 查询）。

- S11（第21-22周）：FIM 补全小模型训练与蒸馏

  - 算法端：准备 Fill-in-the-Middle（FIM）训练语料（从公开代码库提取）。基于 DeepSeek-Coder-1.3B / 6.7B 进行 LoRA 微调，或使用 8x 小模型蒸馏大模型能力。

  - 工程侧：部署专用补全模型（GPU 推理优化，TensorRT/ONNX），目标行级补全延迟 < 300ms，与主模型（慢速）做智能路由分流（简单场景走小模型，复杂推理走大模型）。

- S12（第23-24周）：原生 IDE 调研与迁移准备

  - 技术预研：Fork VS Code 源码，研究如何深度嵌入 AI 能力（如 Cursor 的 Tab 快捷键、光标预测跳转）。

  - 优化：针对 Builder 模式做“长上下文”优化（如 200K token 输入下的显存优化），支持超大型 Monorepo 仓库。

## 💡 关键风险提示（细化版补充）
1. 上下文长度爆炸：P2 阶段必须强制实施 Token 压缩策略（如提取函数签名而非整个函数体，去除注释和空行），否则 API 费用会失控。

2. 工具执行死循环：P3 阶段的 Agent 必须设定 最大迭代步数（如 15 步） 和 超时熔断（2分钟），防止 AI 在终端里无限重试消耗额度。

3. 索引性能：P2 的 tree-sitter 解析大型 node_modules 会卡死，必须结合 .gitignore 并限制文件大小（<1MB）。

## 📋 建议前置技术选型（细化落地工具）
| 模块	       | 推荐选型                                     |
|------------|----------------------------------------------|
| 插件端	     | VS Code Extension API + Webview（React）     |
| 后端框架   | 	Python FastAPI 或 Node.js NestJS（流式友好） |
| 本地向量库	 | LanceDB（嵌入式，免安装）或 Qdrant           |
| AST 解析   | 	tree-sitter（多语言统一）                    |
| Agent 框架 | 	LangGraph 或 自研轻量级状态机（更可控）      |
| 沙箱	       | Docker SDK 或 nsjail（轻量级）               |
