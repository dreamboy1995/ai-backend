
## Sprint 5
这个 Sprint 是 "让AI真正懂你的代码库" 的核心。S4 只是把代码"切碎并编号"（向量化），而 S5 要解决的是 "用户提问时，如何从海量碎片中精准捞出最相关的几块，并塞进 Prompt"。这是决定 AI 回复质量从"及格"跃升到"惊艳"的关键。

### 核心目标（S5）
混合检索与智能上下文组装：实现 BM25（关键词）+ 向量（语义）+ 符号（精确）的三路混合检索；引入 Rerank（重排序）模型精选 Top-K；实现基于 Token 预算的动态上下文组装器，让 AI 回复时"该看的代码都看到了"。


### 👥 人员分工（S5 重点在算法调优）
- 后端/算法开发（1-2人）：BM25 索引构建、RRF（倒数排名融合）、重排序模型集成、上下文组装器（含 Token 压缩策略）。
- 插件开发（1人）：在 Chat UI 中展示"引用了哪些代码片段"的可视化引用来源（Citation），增强用户信任感。


### 📅 每日拆解任务（第 41-50 个工作日）
#### 第 41-42 天（BM25 关键词检索器落地）
| 角色 | 具体任务（粒度到代码模块） | 验收标准 |
|------|--------------------------|---------|
| 后端/算法 | 1. 安装 `rank-bm25` 库：`pip install rank-bm25`。<br>2. 编写 `bm25_index.py`：<br>  - 遍历 S4 中已存入 LanceDB 的所有 Chunk，提取 `content` 字段。<br>  - 使用 Jieba（中文）和空格分词（英文）构建词袋（Corpus）。<br>  - 构建 BM25 模型（`BM25Okapi`），序列化保存到本地文件（`./.ai_cache/bm25_index.pkl`），避免每次启动都重建。<br>3. 提供检索函数 `bm25_search(query: str, top_k=20)`，返回与关键词匹配的 Chunk ID 列表及 BM25 原始分数。 | 对"排序算法"提问时，BM25 能优先召回包含"sort"、"quick"、"merge"等关键词的 Chunk（即使向量语义匹配不佳，关键词匹配也要顶上来）。 |
| 插件 | 1. 无新功能开发。配合后端验证文件路径传递格式（统一使用相对路径，如 `src/main.py`）。 | - |

⚠️ 多语言分词坑：Python 的 `rank-bm25` 默认按空格分词，对中文完全无效。必须引入 `jieba` 或 `pkuseg` 预处理。英文代码中驼峰命名（如 `QuickSort`）也需要用正则拆分为 `Quick` + `Sort`，否则搜索"sort"会漏掉 `QuickSort`。


#### 第 43-44 天（三路检索融合 + RRF 排序）
这是 S5 最核心的算法冲刺，要将向量（语义）、BM25（关键词）、符号（精确匹配）三条路的结果融合。

| 角色      | 具体任务（核心算法） | 验收标准 |
|-----------|---------------------|---------|
| 后端/算法 | 1. 编写 `fusion_reranker.py`，实现 RRF（倒数排名融合）算法：<br>  - 公式：`RRF_score(doc) = Σ 1 / (k + rank_i(doc))`，其中 `k=60`（经典值）。<br>  - 输入：向量检索 Top-20、BM25 Top-20、符号精确检索（如用户输入 `#DataProcessor`）Top-10。<br>  - 输出：融合后的 Top-30 候选 Chunk 列表。<br>2. 集成轻量级重排序模型（Cross-Encoder）：<br>  - 加载 `cross-encoder/ms-marco-MiniLM-L-6-v2`（约 90MB）。<br>  - 将 RRF 输出的 Top-30 候选，逐对（Query, Chunk）计算相关性分数，按新分数重排，最终输出 Top-5。<br>  - 设置超时熔断：若重排序耗时 > 300ms，自动跳过重排序，直接使用 RRF 结果（保障延迟）。<br> | 针对模糊提问（如"怎么处理数据流"），向量召回可能乱飘，BM25 可能缺语义，但 RRF + 重排序后，Top-5 中至少 3 个是真正相关的函数。 |
| 后端/算法 |3. 编写测试脚本，对比单独用向量 vs RRF vs RRF+Rerank 在 50 个手工标注的 Query 上的 Hit@5 命中率，输出报表。|在测试报告中，RRF+Rerank 的命中率比纯向量检索至少提升 20 个百分点。|

💡 性能策略：重排序模型跑在 CPU 上可能慢，务必使用 `torch` 的 `eval()` 模式，并设置 `model.to("cpu")`。若对延迟极其敏感，可降级为只对 Top-10 重排，而非 Top-30。


#### 第 45-46 天（符号精确检索 & 依赖图增强）
除了语义和关键词，用户经常输入精确的类名/函数名（如"calculate 函数在哪"），这时必须走精确索引查找。

| 角色 | 具体任务（补齐召回路径） | 验收标准 |
|------|-------------------------|---------|
| 后端/算法 | 1. 编写 `symbol_exact_matcher.py`，利用 S4 提取的符号表（存于 SQLite/JSON），对用户 Query 中的 `#` 引用或明显的驼峰/下划线命名做精确字符串匹配（含模糊前缀匹配）。<br>2. 将匹配到的符号对应的 Chunk 直接插入候选列表，不经过向量检索（节省计算）。<br>3. 增强：若用户问"这个类在哪里被调用了"，利用 S4 构建的依赖关系图（Call Graph），返回所有调用该类的函数列表（即反向依赖查询）。 | 输入 `#DataProcessor`，后端能直接定位到定义该类的文件路径和行号范围。输入"谁调用了 `save()`"，能返回 `main.py` 第 15 行和 `utils.py` 第 88 行。 |
| 插件 | 1. 改进 S4 中预留的 `#` 符号下拉框：当用户输入 `#` 后，调用后端新的 `/v1/symbols/search?q=...` 接口，实时补全符号名（输入"Da"就弹出"DataProcessor"）。 | 输入 `#Da`，下拉框在 300ms 内弹出 `DataProcessor` 和 `DatabaseConnector`。 |


#### 第 47-48 天（智能上下文组装器 & Token 预算控制）
现在能检索到 Top-5 相关代码了，但如何把它们拼进 Prompt 是门艺术。直接塞原文会超 Token，塞太少 AI 看不懂。

| 角色 | 具体任务（核心策略） | 验收标准 |
|------|---------------------|---------|
| 后端/算法 | 1. 编写 `context_assembler.py`，实现智能压缩与拼接：<br>  - 输入：Top-5 Chunk + 当前光标所在文件（隐式上下文）。<br>  - 打分排序：按位置权重调整顺序（光标所在文件的 Chunk 权重 +30%，其他文件的 Chunk 权重正常）。<br>  - 压缩策略（关键）：<br>    a. 若 Chunk 是函数且函数体 < 100 行，保留完整代码。<br>    b. 若 > 100 行，仅保留函数签名（`def`/`class` 行）+ 注释 + 前 10 行 + 后 10 行，中间用 `// ... 省略 N 行 ...` 替代。<br>    c. 最终组装成结构化的 XML（类似 S2 格式），并确保总 Token 数 < 8000（给模型输出留 2000）。<br>2. 如果压缩后仍超 Token，按"低分优先丢弃"策略从最低相关度的 Chunk 开始剔除。 | 在日志中打印组装前后的 Token 计数对比（原始 12000 tokens → 压缩后 7500 tokens），且压缩后的代码片段保留了关键逻辑（不丢核心算法）。 |
| 插件 | 1. 在聊天界面 AI 回复上方，新增一个可折叠的"📎 参考了 N 个代码片段"区域，展示被引用的文件路径（点击可跳转）。<br>2. 数据来源：后端在 SSE 流中新增 `references` 字段（S5 接口变更）。 | 用户提问后，AI 回答上方出现"参考了 `main.py` (第 12-45 行) 和 `utils.js` (第 8-20 行)"，点击即可打开对应文件。 |

⚠️ 关键参数调优：token 预算不能写死。必须根据模型动态调整（DeepSeek 支持 64K，GPT-4o 支持 128K）。建议后端提供一个配置接口，前端在 `globalState` 中存储当前模型的最大上下文长度，上下文组装器按 70% 比例填充（留 30% 给对话历史和模型输出）。

### 📂 关键接口/数据结构变更（S5 新增）
1. 检索接口（用于 `#` 符号实时补全）
```typescript
GET /v1/symbols/search?q=Data&limit=10
Response: {
  symbols: [
    { name: 'DataProcessor', type: 'class', file_path: 'src/models.py', line: 25 },
    { name: 'DataLoader', type: 'function', file_path: 'src/utils.py', line: 88 }
  ]
}
```

2. Chat 请求体新增 `retrieval_config` 配置
```typescript
POST /v1/chat/completions
Request: {
  // ... 原有字段
  retrieval_config: {
    auto_context: true,           // 是否自动从索引中检索（S5 默认开启）
    top_k: 5,                     // 最终注入 Prompt 的片段数
    include_references: true      // 是否在 SSE 流中返回引用列表
  }
}
```

3. SSE 流式响应增加 `references` 元数据块
```typescript
// 在流结束前（或在第一个 chunk 之前），推送一条元数据
data: {"type":"meta","references":[{"file":"src/main.py","lines":"12-45","score":0.92}]}
```


### 🔧 S5 关键技术预研与风险预警（研发必读）
| 风险点 | 应对方案 |
|--------|---------|
| BM25 索引磁盘占用 | 大型仓库（10万+文件）的 BM25 词袋矩阵可能膨胀到数 GB。解决方案：限制索引文件大小，只索引最近 6 个月修改过的文件或不包含 `test_` 前缀的文件（忽略测试目录）。 |
| 重排序模型显存不足 | Cross-Encoder 模型虽然只有 90MB，但在 CPU 上运行 `model.predict()` 对 30 个候选做逐对推理时，单次 Query 耗时可能飙到 1 秒。优化方案：将 Top-30 候选合并成一条文本（用 `[SEP]` 分隔）一次性输入模型做多分类，或限定重排序候选数 ≤ 10。 |
| 上下文组装导致的"信息过载" | 有时塞入 5 个 Chunk 会让 AI 过度关注检索内容而忽略用户的核心指令。策略：在 System Prompt 中明确指示"Context 仅供参考，用户的最新指令优先级最高"，防止 AI 被干扰。 |
| 引用信息丢失 | 大模型的 SSE 输出是增量流，`references` 可能到达时 Webview 还未渲染完毕。务必在前端设计状态机：先收到 `type:meta` 时存储引用列表，流结束时统一渲染。 |
